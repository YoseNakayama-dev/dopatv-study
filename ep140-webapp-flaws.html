#40 ・ 第3章 情報セキュリティにおける脆弱性

Webアプリの仕様と実装による脆弱性 設計の穴と実装の穴

  1. 不備は、仕様（設計）の不備と実装の不備に分けられる。同じ脆弱性でも原因で直し方が変わる。
  2. 型は、入力の扱い・出力の扱い・認証認可と状態の3つ。共通の原因は、値と状態を信用しすぎること。
  3. 設計で業務ルールを洗い出し、サーバ側で毎回検証する。WAFは補助で、業務ロジックの不備は防げないことが多い。

用語カード

クイズ

  1. 動画で出た問題Webアプリの不備への対策として、適切なのは？

    1. 画面側の検証は、迂回できる

    2. 見た目では、強制にならない

    3. サーバ側での検証

    4. 内部の情報が、手がかりになる

  2. パスワードの試行回数に制限を設けない仕様のまま、コードは仕様どおりに正しく実装されている。この不備の分類と直し方として適切なのはどれか。

    1. コードは仕様どおり。回数制限の考慮漏れは、実装ではなく仕様の不備。

    2. 正解。回数制限は仕様（設計）の考慮漏れの例。コードだけでは直らない。

    3. エラー表示の問題ではない。エラーの汎用化は内部情報を見せない対策。

    4. WAFは補助で、業務ロジックの不備は防げないことが多い。

  3. ポイント交換の機能が「申込→承認→交換」の順で作られているが、交換の処理を直接要求すると、承認されていなくても実行できる。対策として適切なのはどれか。

    1. 正解。処理の順序と状態は、サーバ側で毎回検証する。

    2. 画面側の制御だけでは、順序は強制にならない。

    3. プレースホルダはSQLの組み立ての対策。順序の検証漏れは別の問題。

    4. WAFは補助で、業務ロジックの不備は防げないことが多い。

  4. 例外が起きたとき、画面にSQL文や内部の処理の詳細が表示された。この不備の分類と対処として、適切なのはどれか。

    1. 詳細情報の表示はエラー処理の不備。プレースホルダは入力の扱いの対策。

    2. HTMLエスケープは出力の文脈に応じた対策で、詳細な情報の表示を防ぐものではない。

    3. 権限の問題ではなく、内部の詳細を見せてしまうエラー処理の問題。

    4. 正解。内部の情報は攻撃の手がかりになるので、エラーは汎用の表示にする。

  5. 調査記録によると、利用者が他人の注文番号を指定すると他人の注文内容が表示され、サーバ側に所有者を確認する処理が無かった。分類と対処として適切なのはどれか。

    1. SQLの組み立ての問題ではない。プレースホルダでは認可の漏れは直らない。

    2. 正解。認可チェックの漏れは認証・認可・状態の型。認可は毎回サーバ側で確認する。

    3. エスケープは出力の対策で、認可の漏れを直すものではない。

    4. 画面側の制御だけでは強制にならない。認可はサーバ側で確認する。

  6. WAFを導入したので、設計段階の洗い出しやテストは省略してよいという提案があった。評価として適切なのはどれか。

    1. 正解。WAFは補助。設計で洗い出し、サーバ側で検証し、テスト・診断・レビューで見つけて直す。

    2. サーバ側で入力値・認可・状態を毎回検証する。WAFで代わりにはならない。

    3. 設計の段階で業務ルールと脅威を洗い出し、要件に入れる。診断だけでは代わりにならない。

    4. 業務ロジックの不備はWAFでは防げないことが多い。

頭の中で考える

  1. 同じ脆弱性でも、原因が設計か実装かで直し方が変わるのはなぜか。頭の中で説明してみよう。

    答えを開く

    設計の不備は業務ルールや状態遷移、回数制限などの考慮漏れなので、コードを直すだけでは足りず、脅威と業務ルールを洗い出して要件に入れる。実装の不備は検証・エスケープ・認可チェックの漏れなので、コードで直す。

    思い浮かんだ要素にチェック

  2. 画面側の制御だけで処理の順序を守らせるのが不十分な理由と、あるべき対策を、頭の中で説明してみよう。

    答えを開く

    画面側の制御では順序は強制にならず、サーバが受け取った値や状態を信用しすぎることが原因になる。サーバ側で入力値・認可・処理の状態を毎回検証する。WAFは補助で、業務ロジックの不備は防げないことが多い。

午後問題にチャレンジ

ECサイトの購入機能の調査記録（ダミー）
対象: ECサイトの購入機能（ダミー）。購入は「カート→確認→決済→完了」の順に進む
決済の画面を経由せず、完了画面のURLへ直接要求した注文が、支払い未了のまま確定
完了画面の処理は、注文番号を受け取ると、そのまま注文を確定していた
要求は、利用者本人のログイン状態で、本人の注文番号に対して行われていた
// 注文番号は、プレースホルダでSQLに渡されており、SQLの組み立てに問題はない

この事象の原因として、適切なのは？

答えを開く

決済を経たかをサーバ側で検証していない、処理の順序の不備

よくある誤答

  • IDOR（他人の注文番号を指定する不備） … 要求は、本人の注文番号
  • SQLインジェクション … 入力はプレースホルダでSQLに渡されている

  • 3.6.5 Webアプリケーションの仕様や実装による脆弱性と対策

不備を仕様（設計）と実装に分け、入力・出力・認証認可と状態の3つの型に整理して、原因ごとの直し方の違いを確かめながら読む。
