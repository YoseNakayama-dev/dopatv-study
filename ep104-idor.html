認可不備 IDOR/BOLA 認可チェックが抜けると何が起こる？

  1. IDOR/BOLAは、URLなどのIDを書き換えられ、オブジェクト単位の認可チェックが無いと成立する。
  2. 根本対策は、利用者IDをセッションから取り、参照・更新・削除のたびに所有者を確認すること。
  3. 推測しにくいIDは補助、WAFでは防げない場合がある。共有データはポリシーやロールで判断する。

クイズ

  1. 動画で出た問題他人の注文が見える脆弱性の根本対策は？

    1. 推測しにくくなるが補助にとどまる

    2. リソースごとに認可を確認する

    3. 通信が正常に見え、防げない場合がある

    4. 認証の強化で、認可の代わりではない

  2. 注文取得APIが、POSTの隠し項目 user_id を検索条件に使い、ログイン済みか否かだけを確認している。修正として最も適切なものはどれか。

    1. 正解。利用者IDは外部から受け取らず、セッション変数から取る。

    2. 識別子の暗号化は安全に行うのが難しく、避ける。認可チェックの代わりにもならない。

    3. ランダムなIDは多層防御としてのみ有効で、チェックの欠落は直らない。

    4. 送る場所を変えても、外部の値をそのまま信用する点は変わらない。

  3. 請求書APIで、他人の請求書の番号を指定されたとき、請求書が存在すること自体も知られたくない。応答の方針として最も適切なものはどれか。

    1. 応答が分かれると、番号が存在することを推測できてしまう。

    2. エラーの詳細を出すと、かえって情報を与える。

    3. 応答が異なるので、存在の有無を見分けられてしまう。

    4. 正解。存在が機微なら、両方の場合で同じ応答（例: 404）にそろえる。

  4. 請求書APIのIDORを確認するテストの方法として最も適切なものはどれか。

    1. 管理者の権限では、他人のデータを拒否できるかを確かめられない。

    2. ID が予測可能かどうかによらず拒否されることを確かめる必要がある。

    3. 正解。権限の異なる複数アカウントで、参照を書き換えて他人のオブジェクトの読み書き・削除が拒否されるかを見る。

    4. 通信は正常に見えるので、WAFのログには残らない場合がある。

  5. 文書を同じ部署の他の人にも共有する機能で、認可を「文書の所有者IDとログイン中の利用者IDの一致」だけで判定している。この設計の評価として最も適切なものはどれか。

    1. 毎回の確認は必要だが、所有者との一致比較だけでは足りない場合がある。

    2. 正解。共有データはポリシーやロールで判断する。IDの一致比較だけでは完全な対策にならない。

    3. 識別子の暗号化は安全に作るのが難しく、共有の判断も解決しない。

    4. ランダムなIDは補助にとどまり、認可チェックの代わりにはならない。

  6. 一般利用者が、管理者向けの一括出力機能のAPI（/api/admin/export）を直接呼べた。各オブジェクトの所有者チェックは実装済みである。この不備の分類として最も適切なものはどれか。

    1. 正解。機能（関数）単位の不備は別の項目（BFLA）。機能ごとの認可も必要になる。

    2. 所有者チェックは実装済みなので、足りないのはオブジェクト単位ではなく機能単位の認可。

    3. ログインはできている。範囲を決める認可の話で、認証の強化では直らない。

    4. IDの推測は関係しない。ランダムなIDはそもそも補助にとどまる。

頭の中で考える

  1. 注文番号を連番から長いランダムな値に変えただけでは、IDORの対策として足りない理由を、頭の中で説明してみよう。

    答えを開く

    原因は認可チェックの欠如で、IDの推測しにくさは補助にとどまる。IDが漏れたり知られたりすれば、チェックが無い限り他人のデータに届く。チェックが正しく実装されていればIDが漏れても守れる。

    思い浮かんだ要素にチェック

  2. 注文の参照APIには所有者チェックを入れたが、更新・削除APIには入れ忘れた。何が起こり、どう直すかを頭の中で説明してみよう。

    答えを開く

    更新・削除でも、他人のデータを書き換えたり消したりできてしまう。利用者IDをセッションから取り、参照・更新・削除のすべてで所有者を確認する。

    思い浮かんだ要素にチェック
