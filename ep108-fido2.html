#8 ・ 追加テーマ（目次外）

FIDO2・WebAuthn 秘密を渡さずに本人だと示す

  1. FIDO2は公開鍵暗号を使い、サイトごとの鍵ペアの秘密鍵は認証器にとどめ、サーバは公開鍵だけを保存する。
  2. 鍵はRP ID（ドメイン）に紐づき、作成したサイトのオリジンでしか使えないため、偽サイトに強い設計。
  3. 万能ではない。認証後のセッション盗用や端末のマルウェアは別の課題で、絶対安全とは言えない。

クイズ

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題FIDO2の認証の説明として適切なのは？

    1. パスワード認証の説明

    2. 秘密鍵は端末にとどめ、署名で示す

    3. 生体情報は端末の中にとどまる

    4. コード送付型の認証の説明

  2. FIDO2だけでログインさせるサイトのデータベースが漏えいした。保存されていた認証情報について最も適切な説明はどれか。

    1. 秘密鍵は認証器にとどまり、サーバには保存されない。

    2. 生体情報は端末内にとどまる。サーバには、ローカル検証に成功した結果だけが渡る。

    3. 正解。サーバには共有する秘密が無く、保存されるのは公開鍵だけ。そのまま認証に使える情報は含まれない設計。

    4. FIDO2のみのサイトでは、パスワードを保存しない。

  3. 認証器が、ボタンへのタッチだけで署名する設定になっている（指紋やPINは要求しない）。説明として最も適切なものはどれか。

    1. 正解。本人存在確認（UP）と本人確認（UV）は別。タッチだけでは、操作している人が本人かは確かめない。

    2. タッチは存在の確認で、本人確認ではない。区別して扱う。

    3. 署名の検証は公開鍵で行うが、署名を生成する操作の条件は安全性に影響する。

    4. 生体情報はサーバに送られず、端末内で検証される。

  4. FIDO2だけでログインできるようにしたサイトで、ログイン後のセッションIDがXSSで盗まれた。評価として最も適切なものはどれか。

    1. FIDO2が守るのは認証の場面。ログイン後のセッションIDは別に守る必要がある。

    2. 正解。認証後のセッションの盗用は別の課題。セッション管理やXSS対策が別に要る。

    3. 署名の検証は認証時の話で、ログイン後のIDの再利用を防ぐものではない。

    4. 鍵の紐づけは認証の場面での話。XSSによる盗用を防ぐ仕組みではない。

  5. WebAuthnで、新しい鍵ペアを作る登録処理と、チャレンジに署名する認証処理で呼ぶAPIの組み合わせとして正しいものはどれか。

    1. 登録と認証が逆になっている。

    2. 認証では get を呼ぶ。create は登録用。

    3. 登録に使うのは create。store は取り違えやすいが、ここでの登録用ではない。

    4. 正解。登録は navigator.credentials.create、認証は navigator.credentials.get。

  6. 利用者が共用PCから認証する運用で、PCに内蔵の認証器が使えない。FIDO2を使い続けるための選択肢として最も適切なものはどれか。

    1. 秘密鍵は認証器にとどめる設計。サイトに預けると前提が崩れる。

    2. 生体情報は端末内にとどまり、サーバには登録しない。

    3. 正解。外部のセキュリティキー（ローミング型）なら、内蔵の認証器が無いPCでも使える。

    4. メールでコードを送る方式はFIDO2ではなく、別の方式。

頭の中で考える

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. 偽サイトにFIDO2で認証しようとしても、攻撃者がログインできない理由を、頭の中で説明してみよう。

    答えを開く

    鍵は作成したサイトのドメイン（RP ID）に紐づき、そのオリジンでしか使えない。偽サイトでは正規サイト向けの鍵が使われず、正しい応答を作れない。パスワードのように使い回せる秘密を渡さない点も一因。

    思い浮かんだ要素にチェック

  2. 「FIDO2にすれば、もうアカウント乗っ取りは起きない」と言い切れない理由を、頭の中で説明してみよう。

    答えを開く

    FIDO2が守るのは認証の場面。認証後のセッションの盗用や、端末自体のマルウェアは別の課題で、別の対策が要る。「絶対安全」とは言えず、運用とセットで考える。
