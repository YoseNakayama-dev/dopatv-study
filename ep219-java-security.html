#119 ・ 第8章 システム開発におけるセキュリティ対策

Javaのセキュリティ 実行環境の機構・留意点・例外処理

  1. Javaは検証・クラスローダ・ポリシーで実行を絞る。ただしセキュリティマネージャはJava 17で非推奨。
  2. 公開範囲は最小に。finalは参照の付け替えを防ぐだけで、可変オブジェクトの中身は防御的コピーで守る。
  3. 例外は握りつぶさず、内部情報は画面に出さずログへ。認可で例外が出たら許可せず拒否に倒す。

クイズ

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題Javaの説明として、適切なものは？

    1. 検証はクラスの読み込み時

    2. 防御的コピーが有効

    3. 握りつぶすと異常に気付けない

    4. クラスローダは読み込みを管理

  2. 不変にしたいクラスで、フィールドはprivate、クラスもfinalにした。ただしgetterが、内部にある可変オブジェクト（日付など）の参照をそのまま返している。外部から中身を書き換えられるのを防ぐ対応はどれか。

    1. 正解。可変オブジェクトは受け渡しのときに複製（防御的コピー）を使うと、返した参照経由で中身を書き換えられなくなる。

    2. フィールドのfinalは参照の付け替えを防ぐだけで、参照先の可変オブジェクトの中身は変更できてしまう。

    3. 前提ですでにクラスはfinalで、継承による改変は防げている。返された参照経由の変更は、これでは止まらない。

    4. 入力値の検証は外部からの入力を使う前の対策。ここでの問題は、内部の参照を外へ返している点にある。

  3. 認可チェックで、権限情報のDBへの問い合わせが例外になることがある。現在の実装は、例外を捕捉してログに記録したあと、処理を許可として続行している。改善として最も適切なものはどれか。

    1. 通知は気付くための補助にはなるが、許可のままでは権限のない操作が通りうる。例外時の扱い自体を変える必要がある。

    2. 例外を一律に扱うだけでは、失敗したときに許可するかどうかが決まらない。認可の処理で例外が出たら、許可せず拒否に倒す。

    3. 正解。認可の処理で例外が出たら許可せず拒否に倒す。原因の調査のため、詳細はログに記録する。

    4. スタックトレースなどの内部情報は利用者の画面に出さず、ログに記録して調査に使う。

  4. 新規のJavaシステムの設計レビューで、外部から受け取ったコードを、セキュリティマネージャとポリシーで許可範囲に絞って動かす案が出た。留意点として最も適切なものはどれか。

    1. 許可範囲を絞る機構ではあるが、それを唯一の防御とする根拠はない。そのうえ機構自体がJava 17で非推奨になっている。

    2. バイトコード検証は、クラスの読み込み時に不正なバイトコードを検査するもの。ポリシーによる動作範囲の制限とは役割が違う。

    3. 署名付きコードで確認できるのは提供元。許可した範囲に動作を絞る制御とは別のもの。

    4. 正解。セキュリティマネージャはJava 17で削除予定として非推奨になった。新規設計の前提にはしない。

  5. ファイルを開いて処理するメソッドで、途中で例外が起きるとclose()が呼ばれず、ファイルが開いたまま残ることがある。確実に後始末を行う書き方として適切なものはどれか。

    1. 最後の行に書いたclose()は、途中で例外が起きると実行されない。例外時にも実行される場所に書く必要がある。

    2. 入力の検証は有効でも、例外が起きる可能性をなくせるとは言えない。例外が起きたときの後始末は別に必要。

    3. 正解。後始末はfinallyやtry-with-resourcesで確実に行う。例外が起きても解放処理が実行される。

    4. 例外を握りつぶすと異常に気付けなくなる。資源の解放を確実に行う方法にもならない。

  6. 外部システムから受信した、Javaのシリアライズ済みデータを、受信側でそのままオブジェクトに復元している。対応として最も適切なものはどれか。

    1. ログは事後の調査に役立つが、信頼できないデータを検証せずに復元してよい理由にはならない。

    2. 正解。信頼できないデータのデシリアライズは、避けるか検証する。

    3. finalは継承による改変を防ぐもの。復元されるデータが信頼できるかどうかとは別の話。

    4. バイトコード検証はクラスの読み込み時にバイトコードを検査するもので、復元するデータの中身を検査するものではない。

頭の中で考える

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. 認可の処理で例外が出たとき、許可と拒否のどちらに倒すべきか。その理由を頭の中で説明してみよう。

    答えを開く

    拒否に倒す。例外時に許可として続行すると、権限確認ができていない操作が通りうるため。例外を握りつぶさず、詳細はログに記録して調査に使う。

    思い浮かんだ要素にチェック

  2. finalを付けたのに、可変オブジェクトの中身を書き換えられてしまう。なぜか、どう防ぐかを頭の中で説明してみよう。

    答えを開く

    finalは参照の付け替えを防ぐだけで、参照先の可変オブジェクトの中身は変更できるため。受け渡しのときに複製を取る防御的コピーで、中身の変更を防ぐ。

Webアプリの障害記録（ダミー）
Webアプリ: 認証処理で、DB接続の例外が発生
画面に、スタックトレースとDBの接続先が表示された
どこでも捕捉されない例外は、既定のエラー画面に出る
要件: 画面に内部情報を出さず、原因は調査できること

適切な対策は、どれ？

答えを開く

例外を捕捉し、認証は失敗として扱い、画面は汎用の文言、詳細はログに記録する

よくある誤答

  • 例外を捕捉して何もしない … 原因が記録されず、調査できない
  • 例外を投げ直すだけで、どこでも捕捉しない … 既定のエラー画面に出てしまう
