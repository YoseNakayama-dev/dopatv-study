OAuth・OIDC・SAML 認可コードフローとトークン検証

  1. 認可コードはブラウザ経由でリダイレクトURIに返り、クライアントが認可サーバと直接通信してトークンに交換する。
  2. PKCEは乱数のハッシュを認可要求に付け、交換時に元の乱数を求める。リダイレクトURIの厳密な照合は省けない。
  3. IDトークンは署名・発行元・宛先・期限・nonceを検証する。SAMLも署名・Issuer・Audience等を確かめる。

用語カード

クイズ

  1. 動画で出た問題IDトークンを受け取ったクライアントの検証として、適切なものは？

    1. 宛先(aud)の確認が必要

    2. 署名と宛先の確認は別

    3. 期限切れは受け入れない

    4. 発行元が想定どおりか確認する

  2. 認可サーバがPKCEを必須にしたため、リダイレクトURIの照合は緩くても構わないという意見が出た。対応として最も適切なものはどれか。

    1. PKCEは交換時に元の乱数を求めてコードの横取りに備えるが、リダイレクトURIの厳密な照合の代わりにはならない。

    2. 正解。PKCEはコードの横取りへの対策で、リダイレクトURIの厳密な照合の代わりにはならない。

    3. stateは要求と応答の対応づけ（CSRF対策）で、奪われたコードの交換を止めるものではない。併用してもURIの照合は省けない。

    4. トークンの有効期限を短くしても、コードの交換自体は止められない。URIの照合を緩める理由にならない。

  3. SPが受け取ったSAMLアサーションを検証したところ、署名は正しく、有効期限内で、Issuerも想定のIdPだった。ただしAudienceは別のサービスを指していた。処理として最も適切なものはどれか。

    1. 署名と期限が正しくても、Audience（宛先）の確認は別に必要。確認しないと、別のサービス向けの証明を受け入れてしまう。

    2. SAMLも署名・Issuer・Audience・有効期限等を検証する。宛先の確認を省くと、別のサービス向けの証明を受け入れてしまう。

    3. 正解。Audienceが自サービス向けでなければ、署名などが正しくても受け入れない。

    4. 問題文では署名は正しい。署名の確認と宛先の確認は別の確認なので、署名が正しくても宛先は別に確かめる。

  4. スマートフォンアプリが認可コードフローを使う。設計案は、アプリ内に埋め込んだクライアントシークレットで交換を認証し、PKCEは使わないというものだった。評価として最も適切なものはどれか。

    1. 公開クライアントは秘密を安全に持てない。アプリに埋め込んだシークレットは、交換の認証に頼れない。

    2. 公開クライアントは秘密を安全に持てない。PKCEは、元の乱数を交換時に求める別の仕組み。

    3. 認可コードがブラウザ経由で返るのは、認可コードフローの通常の流れ。PKCEは、そのコードの横取りへの対策として使う。

    4. 正解。ネイティブアプリなどの公開クライアントは秘密を安全に持てないため、PKCEで元の乱数の提示を求める。

  5. クライアントが受け取ったIDトークンは、署名・発行元・宛先・期限がすべて正しい。しかし、中のnonceが認可要求時に送った値と異なっていた。処理として最も適切なものはどれか。

    1. 正解。要求時のnonceとの一致も、IDトークンの検証項目のひとつ。一致しなければ受け入れない。

    2. nonceの一致は検証項目のひとつ。ほかの項目が正しくても、省略できない。

    3. stateは要求と応答の対応づけ（CSRF対策）。IDトークンの検証では、要求時のnonceとの一致を別に確かめる。

    4. PKCEはコード交換時に元の乱数を求める仕組みで、コードの横取りへの対策。IDトークンのnonceの一致という検証項目の代わりにはならない。

  6. あるサービスは、OAuthで受け取ったトークンを「利用者がログインした証明」としてそのまま扱っている。設計の見直しとして最も適切なものはどれか。

    1. OAuthは認可の枠組み。認証結果は、OIDCがその上に加える署名付きのIDトークンで伝える。

    2. 正解。OAuthは認可、OIDCがその上に認証を加え、署名付きのIDトークン（JWT）で認証結果を伝える。受け取ったら署名・発行元・宛先・期限・nonceを検証する。

    3. SAMLも署名・Issuer・Audience・有効期限等を検証する。置き換えても検証は省けない。

    4. IDトークンは署名付きのJWTで、署名で改ざんの有無を確かめる。署名を検証せずに中身だけ読むのは誤り。

頭の中で考える

  1. PKCEが認可コードの横取りにどう備えるかと、それでも残る限界を、頭の中で説明してみよう。

    答えを開く

    認可要求に、乱数（code_verifier）のハッシュ（code_challenge）を付ける。コード交換時に元の乱数を提示させ、認可サーバがハッシュと対応するか照合する。コードだけ奪われても、元の乱数を知らなければ交換できない。限界として、リダイレクトURIの厳密な照合の代わりにはならず、乱数ごと奪われる場合は防げない。

    思い浮かんだ要素にチェック

  2. IDトークンを受け取ったクライアントが確かめる項目を挙げ、署名の確認だけでは足りない理由を説明してみよう。

    答えを開く

    署名（改ざんの有無）、発行元iss、宛先aud（自分のクライアントID）、期限exp、要求時のnonceとの一致を確認する。署名が正しくても、宛先を確かめないと別のサービス向けの証明を受け入れてしまう。SAMLも、署名・Issuer・Audience・有効期限等を同様に検証する。

午後問題にチャレンジ

認可コード受け渡しの調査記録（ダミー）
クライアントは、ネイティブアプリで、秘密を持てない
リダイレクトを、端末上の別アプリも受け取れる
別アプリが、認可コードをトークンへ交換しようとした
要件: コードを奪われても、トークンを渡したくない

要件を満たす対策として、適切なのは？

答えを開く

認可要求に乱数のハッシュを付け、交換時に元の乱数を求める

よくある誤答

  • 認可要求のstateを、応答で照合する … stateは要求と応答の対応づけ。別アプリによるコードの交換は止められない
  • トークンの有効期限を、短くする … 期限を短くしても、コードの交換は止められない
