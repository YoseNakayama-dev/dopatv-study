HTTPリクエストスマグリングとキャッシュポイズニング 解釈の差を突く攻撃

  1. 前段と後段で要求の区切りの解釈が食い違うと、スマグリングが成立しうる。
  2. キーに含まれない入力が応答を変えると、細工された応答が保存され他の人に届く。
  3. 解釈・設定・更新をそろえ曖昧な要求は拒否する。WAFだけでは解釈の差は消えない。
用語 9クイズ 6考える 2午後本

用語カード

クイズ

  1. 動画で出た問題HTTPの攻撃の説明として、適切なものは？

    1. 境界の解釈の食い違い

    2. 暗号化と境界の解釈は無関係

    3. HTTPの保存された応答の細工

    4. 解釈の差は消えない

  2. ある構成では、前段と後段が同じ規則で要求の長さを解釈し、長さの指定が二通り付いた要求は前段で拒否している。担当者は「後段への接続を使い回しているので、スマグリングは成立する」と判断した。評価として最も適切なものはどれか。

    1. 使い回しは影響を広げる条件であって、成立の条件ではない。解釈が一致していれば、使い回しだけで成立するとは言えない。

    2. 拒否は有効な対策だが、実装・設定・更新は前段と後段でそろえ続ける必要がある。後段を確認しなくてよいとは言えない。

    3. 正解。成立に必要なのは前段と後段の解釈の差で、使い回しは影響を広げる条件にとどまる。

    4. 使い回しをやめると影響の広がりは抑えられうるが、解釈の差が残るかぎり原因は解消しない。起きないと言い切れない。

  3. CDNは、一部の入力をキーに含めずに応答を保存している。調査で、そのキーに含まれない入力が応答の内容を変えており、変わった応答が同じキーの要求をした他の利用者にも返ることが分かった。対策として最も適切なものはどれか。

    1. 期限を短くすると被害の時間は縮まりうるが、キーに含まれない入力が応答を変える原因は残る。原因が解消するとは言えない。

    2. DNSキャッシュポイズニングは別の話。今回の問題は、HTTPキャッシュのキーと応答の内容の関係にある。

    3. 暗号化しても、キーに含まれない入力が応答を変える問題は残る。暗号化は、保存される応答の内容や、何をキーに含めるかを決めるものではない。

    4. 正解。応答を変える入力はキーに含めるか無視する。個人向け・動的な応答はCache-Control等で保存させない。

  4. ログイン後のマイページの応答（利用者ごとに内容が異なる）がCDNに保存され、同じURLを要求した別の利用者に表示された。調査では、要求の区切りの食い違いは見つかっていない。まず見直すべきものはどれか。

    1. 長さの解釈をそろえるのはスマグリングへの対策で、区切りの食い違いが見つかっていないこの状況の原因とは別。そろえても、保存の可否やキーの設定は変わらない。

    2. 正解。個人向け・動的な応答はキャッシュに保存させない。あわせて、応答を変える入力がキーに含まれているかを確認する。

    3. 期間を長くすると、他の人に返る時間が延びる。同じキーの要求に保存した応答を返すのがキャッシュなので、悪化する。

    4. WAFの遮断ルールは、キャッシュの保存の可否やキーの設定とは別の話。遮断ルールを足しても、保存の設定が変わらないかぎり問題は残る。

  5. 前段の製品を製品の提供元が、後段のアプリを開発会社が、それぞれ単体で診断し、どちらも「指摘なし」だった。結合後の構成に対する評価として最も適切なものはどれか。

    1. 解釈の差は前段と後段の組み合わせで生じる。各段が単体で正しく動いていても、段ごとに規則が違えば食い違いうる。

    2. 要求の区切りは前段も判断する。成立の条件は前段と後段の解釈の差なので、片方だけを見ても足りない。

    3. 正解。解釈の差は前段と後段の組み合わせで現れる。診断は連ねた構成で確認し、実装と設定をそろえる。

    4. WAFだけでは解釈の差は消えない。WAFを足しても、組み合わせの確認を省く理由にはならない。

  6. 後段のアプリサーバを最新版に更新した。前段のプロキシは再起動が必要なので、当面は据え置く方針である。この方針に対する評価として最も適切なものはどれか。

    1. 後段だけを新しくすると、前段との間で解釈が食い違う場合もある。解釈の差は、段どうしの組み合わせで決まる。

    2. 前段も要求の区切りを判断する立場にある。前段が解釈に関わらないという前提は、スマグリングの成立条件と合わない。

    3. 実装・設定・更新のどれもそろえる対象。設定値が同じでも、実装や版が違えば併記時の扱いが違いうる。

    4. 正解。前段と後段で実装・設定・更新をそろえる。片方だけの更新は差を生みうるので、組み合わせで確認する。

頭の中で考える

  1. リクエストスマグリングが成立する条件と、被害が他の利用者に及ぶ理由を頭の中で説明してみよう。

    答えを開く

    前段と後段が連なる構成で、要求の区切りの解釈が食い違うと成立しうる。典型的な原因は、長さを示す二つの方法（Content-Lengthとチャンク転送）の併記時の扱いが段ごとに違うこと。要求の余りが次の要求の先頭に付き、後段への接続を使い回す構成では他の利用者に広がる。

    思い浮かんだ要素にチェック

  2. HTTPキャッシュポイズニングが成立する仕組みと、対策の要点を頭の中で説明してみよう。

    答えを開く

    キャッシュは同じキーの要求に保存した応答を返す。キーに含まれない入力が応答の内容を変えると、細工された応答が保存され、同じキーの他の利用者に有効期限まで届く。応答を変える入力はキーに含めるか無視し、個人向けの応答は保存させない。DNSのキャッシュポイズニングとは別。

    思い浮かんだ要素にチェック

午後問題にチャレンジ

リバースプロキシ構成の診断記録（ダミー）
構成: 利用者 → 前段のリバースプロキシ → 後段のアプリ
前段は、後段への接続を複数の利用者で使い回す
診断: 前段と後段で長さの解釈が食い違い、余りが次の人に付いた
接続の使い回しは性能のため維持。後段はHTTP/1.1のみ
要件: 他の利用者の要求に、影響を及ぼさせない

適切な対策は、どれ？

答えを開く

前段と後段で要求の解釈をそろえ、曖昧な要求は拒否する

よくある誤答

  • TLSの暗号強度を上げる … 経路の暗号化は、要求の区切りの解釈に関係しない
  • WAFで特定の文字列を遮断する … 解釈の差は残り、遮断の対象外の形でも起きる
