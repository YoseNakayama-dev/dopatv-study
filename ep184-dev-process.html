#84 ・ 第8章 システム開発におけるセキュリティ対策

開発工程ごとの対策 上流から重ねて防ぐ

  1. 要件・設計・実装・試験の各工程に対策を置く。要件で資産と基準を決め、設計で脅威分析をして対策を入れる。
  2. 実装は規約・レビュー・静的解析で確かめ、試験は動かして入力を与える脆弱性診断を行う。公開後も続ける。
  3. 規約は確認しないと形だけ。静的解析は設計の不備を見つけにくく、試験は確認した範囲の不備しか見つからない。

  1. 動画で出た問題静的解析の説明として、適切なのは？

    1. 動かして調べるのは動的な検査

    2. 実行せず、ソースコードを調べる

    3. 擬似的な攻撃は侵入テスト

    4. 設計書の確認は設計レビュー

  2. 実装工程では、ビルドのたびに静的解析を実行している。一方、設計書に認可の抜けなど、設計上の不備が残っている疑いが出た。対応として最も適切なのはどれか。

    1. 静的解析は設計上の不備を見つけにくい。設計の問題は設計の段階で見つける。

    2. 診断を公開直前に回すと、直す時間が足りない。設計の不備は設計の段階で見つけるほうが早い。

    3. 正解。脅威分析で洗い出した脅威への対策を設計に入れ、設計書はレビューして不備を早く見つける。

    4. 規約は実装での書き方の決まりで、実装工程の対策。設計上の問題は設計の段階で見つける必要がある。

  3. 開発チームはコーディング規約を文書で配布したが、守られているかを確かめる仕組みは用意していない。この状況への評価として適切なのはどれか。

    1. 正解。規約は守られているかを確認しないと形だけになる。レビューや解析で確認する。

    2. 規約は作っても守られなければ意味がない。守られているかの確認が要る。

    3. 静的解析は設計上の不備を見つけにくい。設計の問題は設計の段階で見つける。

    4. 試験は確認した範囲の不備しか見つからない。規約が守られているかは、実装の段階でレビューや解析で確認する。

  4. 試験工程で、試験項目は機能の動作確認だけでセキュリティの項目が無い。全項目に合格した。リリース前の判断として適切なのはどれか。

    1. 試験は確認した範囲の不備しか見つからない。セキュリティの項目が無ければ、その不備は確認されていない。

    2. 公開後も診断と修正を続ける。合格だけで不要にはならない。

    3. 診断を公開直前に回すと、直す時間が足りない。早めに計画して余裕を持つ。

    4. 正解。試験の項目にセキュリティを入れておく。確認した範囲の不備しか見つからないため。

  5. 実装工程で、ビルドのたびにソースコードを自動で調べて欠陥を早く見つけたい。まだシステムを動かせる環境はない。適切な手法はどれか。

    1. 動かして入力を与え、応答から欠陥を探すのは試験工程の脆弱性診断。この状況では動かす環境が無い。

    2. 正解。静的解析は実行せずにソースコードを調べる。ビルドのたびに実行すれば漏れにくい。ただし設計上の不備は見つけにくい。

    3. 侵入テストは擬似的な攻撃を行う試験の手法で、ソースコードを調べる静的解析とは別。

    4. 設計レビューは設計書を確認して不備を早く見つける作業で、ソースコードを調べる静的解析とは別。

  6. 要件定義の段階で、セキュリティ要件の決め方を検討している。適切なものはどれか。

    1. 正解。要件定義で守る資産と満たす基準を決め、セキュリティ要件として文書に残す。

    2. 満たす基準は要件定義で決めて文書にする。静的解析は設計上の不備を見つけにくく、基準の代わりにならない。

    3. 診断を公開直前に回すと直す時間が足りない。基準は要件定義で決める。

    4. 要件は文書に残し、関係者で共有する。口頭では残らない。

頭の中で考える

  1. 「最後にテストすれば安全」と考えてはいけない理由を、頭の中で説明してみよう。

    答えを開く

    試験は確認した範囲の不備しか見つからず、静的解析も設計上の不備は見つけにくい。設計の問題は設計の段階で脅威分析とレビューにより見つける。診断を公開直前に回すと直す時間も足りない。だから上流から工程ごとに重ねて対策する。

    思い浮かんだ要素にチェック

  2. コーディング規約を作ったのに形だけになる条件と、防ぎ方を頭の中で説明してみよう。

    答えを開く

    規約は守られているかを確認しないと形だけになる。レビューや静的解析で守られているかを確認し、ビルドのたびに実行すれば漏れにくい。ただし静的解析は設計上の不備を見つけにくいので、設計の問題は設計の段階で見つける。

午後問題にチャレンジ

Webアプリ開発の現状記録（ダミー）
現状: Webアプリの実装中。開発者は10名で書き方に差がある
過去の不具合は、入力値の検証漏れが多かった
ビルドの仕組みには、検査ツールを組み込める
要件: 個人の差に左右されず、検証漏れを早く見つけたい

要件を満たす対策として、適切なのは？

答えを開く

コーディング規約を定め、ビルドのたびに静的解析を行う

よくある誤答

  • 公開後に脆弱性診断を行う … 要件の『早く見つけたい』に合わない
  • 開発者に、口頭で注意を促す … 個人の差に左右され、要件を満たせない
