SQLインジェクション② 防御の仕組みと限界

  1. 根本対策はプレースホルダ。SQL文の構造を先に確定し、入力は後から値として渡す。
  2. 列名・表名・ASC/DESCなどの識別子はバインドできないので、許可リストで候補を固定する。
  3. エラー非表示・権限最小化は保険的な対策、WAFは運用面の補助。どちらも修正の代わりにならない。

クイズ

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題列名を入力で切り替えたい。適切な対策は？

    1. 識別子はバインドできない

    2. 候補をコード側で固定する

    3. HTMLエスケープはXSS向けの対策

    4. WAFは補助。修正の代わりにならない

  2. 動的プレースホルダの説明として最も適切なものはどれか。

    1. これは静的プレースホルダの説明。

    2. 識別子はどちらの方式でもバインドできない。

    3. 対策にはなる。ただし静的のほうが原理的に確実。

    4. 正解。動的はライブラリ側でエスケープして組み立てるため、安全性はその実装しだい。

  3. 一覧の並び順（ASC/DESC）を利用者が切り替えられるようにしたい。実装として最も適切なものはどれか。

    1. エスケープは値（リテラル）向けの処理。キーワードの位置に入力を入れる作りは残る。

    2. ASC/DESC はキーワードで、値ではないのでバインドできない。

    3. 正解。入力は候補を選ぶ目印にだけ使い、SQLに入る文字はコード側の許可リストで決める。

    4. WAFは補助で、入力を連結する原因は残る。

  4. ストアドプロシージャを呼び出し、引数はプレースホルダでバインドしている。それでもSQLインジェクションが起こりうるのはどの場合か。

    1. 正解。呼び出し方が安全でも、中で動的SQLを連結すれば同じ穴になる。

    2. 呼び出し側の対策としては適切で、原因にはならない。

    3. 被害を抑える保険で、成立の原因にはならない。

    4. 数値として確定させるのは対策側の処理。

  5. 事情でプレースホルダを使えず、文字列連結のままSQLを組み立てる。IPAの整理に照らして適切な対応はどれか。

    1. 外部入力に限らず、SQL文を構成するすべてのリテラルに適用する。

    2. HTMLエスケープはXSS対策で、SQLの文法とは規則が違う。

    3. 長さの制限だけでは、短い攻撃文字列を防げない。

    4. 正解。リテラルを正しく作る。ただし規則はDBごとに違い、OWASPは強く非推奨としている。

  6. 診断でSQLインジェクションが見つかった。改修版のリリースまでしばらくかかる。その間の対応として最も適切なものはどれか。

    1. 正解。WAFは修正が難しい間の補助。検知漏れや誤検知があるので、修正が最優先。

    2. エラーを隠すのは保険で、原因は残る。

    3. 権限の最小化は被害を抑える保険で、修正の代わりにならない。

    4. WAFには検知漏れがあり、修正の代わりにならない。

頭の中で考える

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. 並び順（ORDER BY の列名）を利用者が選べる画面。どこが危険で、どう直すかを頭の中で説明してみよう。

    答えを開く

    列名は識別子なのでプレースホルダで渡せず、連結すると入力が構文になる。候補の列名をコード側の許可リストで固定し、入力は候補を選ぶ目印にだけ使う。

    思い浮かんだ要素にチェック

  2. 「エスケープすればプレースホルダは不要」という意見に、頭の中で反論してみよう。

    答えを開く

    エスケープの規則はDBごとに違い、すべてのリテラルに漏れなく適用し続けるのは難しい。漏れが1つあれば穴になる。OWASPも強く非推奨としており、プレースホルダを基本にして、エスケープは使えない箇所の代替にとどめる。
