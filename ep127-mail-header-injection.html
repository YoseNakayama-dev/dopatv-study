#27 ・ 第2章 情報セキュリティにおける脅威

メールヘッダインジェクション 改行が区切りになる仕組みと対策

  1. 外部入力をメールヘッダの値に出力し、含まれる改行を除去・拒否しないと成立する。
  2. 影響は宛先の追加による第三者宛送信、件名・本文の改変、送信元の評判低下。実際の影響は送信機能による。
  3. 対策はライブラリのAPI、ヘッダ用入力の改行拒否。宛先固定・送信数制限・CAPTCHAは補助。
用語 10クイズ 6考える 2午後本

用語カード

クイズ

  1. 動画で出た問題メールヘッダインジェクションへの、有効な対策は？

    1. 文字数制限では、短い改行も通る

    2. HTMLエスケープはXSS向け。改行は残る

    3. 改行の拒否と送信APIの利用

    4. SPFは送信元の認証。正規サーバ経由は防げない

  2. 問い合わせフォームで宛先をサーバ側で固定した。件名はそのままSubjectヘッダに出力している。「宛先は固定したので安全」という判断の評価として最も適切なものはどれか。

    1. 正解。宛先の固定は補助。ヘッダ用入力の改行を拒否することが中心になる。

    2. 固定は宛先の入力を防ぐ補助で、改行の拒否の代わりにならない。

    3. Subjectに出力される入力でも、改行が除去・拒否されなければヘッダが区切られる。

    4. アドレス形式の検証も補助で、原因である改行の扱いは直らない。

  3. メールヘッダインジェクションの不具合に対して、フォームにCAPTCHAと送信数の制限を入れた。この対応の評価として最も適切なものはどれか。

    1. 制限は補助で、1回の送信でも第三者宛に送られうる点は残る。

    2. CAPTCHAは補助。入力の改行の扱いを直す代わりにならない。

    3. アドレス形式の検証は補助で、改行を拒否する処理とは別。

    4. 正解。送信数の制限やCAPTCHAは補助で、原因の改行の扱いは別に直す。

  4. SPFとDKIMを設定済みのドメインで、フォーム経由の第三者宛送信が起きた。SPF/DKIMに関する説明として最も適切なものはどれか。

    1. 不正な送信が自社の正規のサーバから行われるため、防げない。

    2. 正解。この攻撃は正規のサーバ経由で送られるので、SPF/DKIMでは防げない。

    3. SPF/DKIMで防げない以上、改行の拒否は省けない。

    4. SPF/DKIMのいずれも、正規サーバ経由の送信は防げない。

  5. 問い合わせフォームの不具合で、外部の宛先にも同じメールが届き、自社ドメインの正規メールが相手先で届きにくくなった。この二次的な影響の説明として最も適切なものはどれか。

    1. 正解。送信元の評判低下は影響の一つ。実際の影響は送信機能やライブラリの挙動による。

    2. 原因は入力の改行の扱いで、認証の突破とは限らない。パスワード変更では直らない。

    3. 送信元IPやドメインの評判が下がる影響がある。

    4. 踏み台になるだけでなく、送信元の評判が下がる影響もある。

  6. フォームで入力させた返信先をReply-Toヘッダに出力したところ、アプリが出力していないヘッダが送信メールに追加されていた。原因として最も適切なものはどれか。

    1. 本文の文字数は、ヘッダが追加される原因ではない。

    2. 正解。入力の改行が除去・拒否されず、ヘッダの区切りとして解釈された。

    3. 形式の検証は補助。原因は改行を除去・拒否していないこと。

    4. 送信数の制限は補助で、ヘッダが追加される原因ではない。

頭の中で考える

  1. 問い合わせフォームが第三者宛メールの踏み台にされる仕組みを、成立条件を入れて頭の中で説明してみよう。

    答えを開く

    件名や返信先などの入力がメールヘッダの値として出力され、改行が除去・拒否されていないと、改行でヘッダが区切られて宛先などの新しいヘッダが追加される。結果、第三者宛に自社の正規のサーバから送られる。

    思い浮かんだ要素にチェック

  2. 宛先の固定、送信数の制限、CAPTCHAを入れた。それでも根本対策にならない理由を頭の中で説明してみよう。

    答えを開く

    これらは補助で、原因である入力の改行の扱いは直らない。中心はライブラリのAPIの利用とヘッダ用入力の改行拒否。SPF/DKIMも正規サーバ経由の送信は防げない。

    思い浮かんだ要素にチェック

午後問題にチャレンジ

問い合わせフォームの調査記録（ダミー）
対象: 問い合わせフォーム（ダミー）。管理者宛に1通を送る機能
入力された件名を、そのままSubjectヘッダに出力 / 改行の除去なし
件名の入力値に、改行（CRLF）と、Bcc: 外部アドレス に相当する文字列が含まれていた
送信されたメールに、アプリが出力していないBccヘッダが追加
1回の送信で、外部の宛先にも同じメールが配信されていた
// 送信はすべて、アプリ自身の正規の送信アカウント / 件名の入力は、SQLには使われず、Subjectヘッダにのみ使われる

この事象の原因として、適切なのは？

答えを開く

入力に含まれる改行が、ヘッダの区切りとして解釈された

よくある誤答

  • SMTP認証の突破 … 送信は、アプリ自身の正規の送信アカウントのみ
  • SQLインジェクション … 件名の入力は、Subjectヘッダにのみ使われる

本で読む

  • 2.8.6 メールヘッダインジェクション

ヘッダが改行で区切られる構造、影響の種類と環境依存、API・改行拒否が中心で宛先固定などが補助である点を確かめながら読む。
