#118 ・ 第8章 システム開発におけるセキュリティ対策

BOFを招くC言語の関数 危険な関数・書式文字列・置き換え

  1. gets・strcpy・strcat・sprintf・scanfの%sは、境界を確認しない仕様のためBOFを招く。
  2. 書式文字列の問題はBOFとは別。入力を書式にせず、書式を固定して引数として渡す。
  3. 置き換え先には、コピー先の大きさを終端NULも含めて指定する。置き換えても長さの誤りは残る。
用語 9クイズ 6考える 2午後本

用語カード

クイズ

  1. 動画で出た問題C言語の関数の説明として、適切なものは？

    1. getsは長さを指定できない

    2. snprintfは最大長を指定できる

    3. 入力を書式にしてはならない

    4. 元が長いと終端NULが付かない

  2. char buf[32]; scanf("%s", buf); という入力処理がある。指摘と対応として最も適切なものはどれか。

    1. 正解。幅を指定しない%sには長さの上限がない。長さは終端NULの1バイトも含めて数えるので、幅はその分を除いた値にする。

    2. 32文字を読み込むと、終端NULを含めて33バイトになり、32バイトのbufを1バイト超える。数え違い（off-by-one）である。

    3. getsは読み込む長さを指定できず、使ってはならない。置き換えても長さの問題は解消しない。

    4. 書式文字列の問題は、利用者の入力を書式として渡す場合の話。ここは固定の書式で、幅を指定していない点が問題である。

  3. char dst[16]; に対して snprintf(dst, strlen(src) + 1, "%s", src); と書かれている。srcは外部からの入力で、長さは不定である。指摘として最も適切なものはどれか。

    1. 足す数を変えても、元の長さを基準にしている点は変わらない。指定する長さはコピー先の大きさである。

    2. 正解。指定する長さはコピー先の大きさで、元の長さではない。元が長いとdstを超えて書き込まれる。

    3. 戻り値は書き込まれたはずの長さで、確認しても最大長の指定の誤りは直らない。指定そのものを直す必要がある。

    4. 終端NULを数えていても、元の長さが16バイトを超えればdstの境界を超える。基準がコピー先でない点が問題である。

  4. 利用者が入力したコメント msg を、fprintf(fp, msg); でログファイルに書き出している。脆弱性の対策として最も適切なものはどれか。

    1. 書式文字列の問題はBOFとは別の脆弱性で、原因が違う。strncpyに置き換えても、入力が書式として解釈される点は直らない。

    2. 短くしても、入力が書式として渡される点は変わらない。原因は書式指定が解釈されることで、メモリの漏えいや書き換えにつながりうる。

    3. 配列の大きさは、書式指定が解釈されるかどうかと関係しない。入力が書式として渡されることが原因である。

    4. 正解。対策は、書式を固定して、入力は引数として渡すこと。入力をデータとして扱う。

  5. 仕様上、入力は最大16文字（1文字1バイトとする）で、全文字を保持したい。現状は char buf[16]; に snprintf(buf, 16, "%s", in); で書き込んでいる。対応として最も適切なものはどれか。

    1. 正解。長さは終端NULの1バイトも含めて数える。bufを17バイトにし、指定する長さはコピー先の大きさにそろえる。

    2. 指定する長さはコピー先の大きさにする。bufが16バイトのまま17と指定すれば、境界を超えて書き込みうる。

    3. 全文字を保持するには、終端NULの1バイトも含めて17バイトが要る。長さ指定を減らす方向では、この要件を満たせない。

    4. 16文字に終端NULの1バイトを足した17バイトが必要で、16バイトでは数え違いになる。現状のままで問題ないとは言えない。

  6. BOF対策として、gets・strcpy・sprintfを、すべてfgets・strncpy・snprintfに置き換え、静的解析で危険な関数の検出が0件になった。リリース前の評価として最も適切なものはどれか。

    1. 危険な関数を置き換えても、長さの誤りは残る。検出0件は、境界を超えないことの証明にならない。

    2. 正解。置き換えても長さの誤りは残る。コピー先の大きさや終端NULの数え方といった指定値を、レビューなどで確認する。

    3. 書式文字列の問題はBOFとは別の脆弱性で、これらの関数の置き換えでは解消しない。

    4. 渡す値はコピー先の大きさで、元の入力の長さではない。元が長いとコピー先を超える。

頭の中で考える

  1. 関数を安全なものに置き換えても、BOFが残りうる理由を頭の中で説明してみよう。

    答えを開く

    置き換え先に渡す長さの指定を誤れば、境界を超える。指定する長さはコピー先の大きさで、終端NULの1バイトも含めて数える。1バイトの数え違いでも境界を超えるので、レビューなどで確認する。

    思い浮かんだ要素にチェック

  2. 書式文字列の脆弱性が、BOFとは別である理由と、その直し方を頭の中で説明してみよう。

    答えを開く

    原因は、利用者の入力を書式としてそのまま渡し、書式指定が解釈されること。メモリの内容の漏えいや書き換えにつながりうる。書式を固定し、入力は引数として渡して直す。

    思い浮かんだ要素にチェック

午後問題にチャレンジ

C言語コードの検証記録（ダミー）
コード: name[16]へ、strcpyで入力をコピーする
入力は利用者が与え、長さは最大256バイト
name[16]は構造体の定義で固定。変更できない
検証: 長い入力を与えると、異常終了した
要件: 長い入力でも、範囲外のメモリを壊さない

適切な対策は、どれ？

答えを開く

終端NULを含むコピー先の大きさを上限に、コピーする長さを制限する

よくある誤答

  • コピーの長さに入力の長さを指定 … 入力は最大256バイトで、nameの16バイトを超える
  • nameを広げる … 構造体の定義で固定されており、変更できない
