サプライチェーン攻撃とSBOM 依存関係を見える化する

  1. 依存ライブラリ・ビルド・配布の経路で、正規の成果物に不正が混ざって届く。信頼された経路なので気づきにくい。
  2. 署名は署名者と改ざんの有無を示すだけで、中身の安全は示さない。SBOMも一覧で、それだけでは脆弱性を防げない。
  3. 対策は版の固定とハッシュ検証、取得元・署名の確認、ビルドの権限最小化と記録、SBOMの更新と継続的な照合。

クイズ

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題SBOMの説明として、適切なものは？

    1. SBOMは脆弱性を修正しない

    2. 構成要素と依存関係の部品表

    3. それは署名の役割

    4. SBOMは検知も遮断もしない

  2. ビルドのたびに、依存ライブラリを「最新版」として自動取得している。配布元の成果物に不正が混ざった場合に備える対策として、最も適切なものはどれか。

    1. 署名は署名者と改ざんの有無を示すだけで、中身の安全は示さない。

    2. SBOMは一覧で、それだけでは防御にならない。版の固定とハッシュ検証が対策になる。

    3. 正解。依存の版を固定し、ハッシュで検証する。

    4. この攻撃は、正規の成果物に不正が混ざって信頼された経路で届くため、気づきにくい。信頼された経路でも、版の固定とハッシュ検証が要る。

  3. 社内で開発した部品と同じ名前の部品が、外部に公開されていることがわかった。サプライチェーン攻撃の観点で最も適切な対応はどれか。

    1. 正解。社内用の名称と公開名の混同は対策が必要な論点。混同されないよう管理し、取得元と署名を確認する。

    2. 社内用の名称と公開名の混同は起こりうるから、対策が必要な論点になっている。「ありえない」と断定せず、名称を管理し、取得元を確認する。

    3. 署名は署名者と改ざんの有無を示すだけ。同名の部品との混同を防ぐ手段ではない。

    4. SBOMは構成要素と依存関係の一覧で、それだけでは防御にならない。

  4. ビルド用のサービスアカウントに、広い権限が付いたままになっている。ビルドの秘密情報が漏れると、成果物を差し替えられうる。対策として最も適切なものはどれか。

    1. 署名は署名者と改ざんの有無を示すだけ。ビルドの権限が広いと、成果物への混入を許しうる。

    2. ビルドの権限が広いと、成果物への混入を許しうる。対策は権限を絞り、記録を残すこと。

    3. ビルド環境では、権限を絞り、記録を残すことが対策。記録を残さない運用は逆になる。

    4. 正解。ビルド環境は権限を絞り、記録を残す。

  5. 製品のリリース時に作成したSBOMが、その後更新されないまま保管されている。使っているライブラリの脆弱性が公表された。対応として最も適切なものはどれか。

    1. SBOMは一覧で、公表された脆弱性情報と照合して初めて使える。

    2. 正解。SBOMを更新し、公表された脆弱性情報と継続的に照合すると、影響する製品を速やかに特定できる。

    3. 間接的に使う部品の脆弱性も製品に影響する。SBOMは間接依存も対象にする。

    4. ハッシュ検証は取得した成果物の確認で、脆弱性の有無を示すものではない。脆弱性の影響は、SBOMと公表された脆弱性情報の照合で確かめる。

  6. 配布した成果物に不正が混入した疑いが出たが、その成果物がどのビルドで作られたかを追跡できなかった。事前の備えとして最も適切なものはどれか。

    1. ハッシュ検証は取得した成果物の確認で、来歴の記録とは別の対策。ハッシュを付けても作成元が自動的にわかるわけではない。

    2. 署名は署名者と改ざんの有無を示すだけで、中身の安全は示さない。来歴の記録は追跡しやすくするための別の対策。

    3. 正解。成果物の来歴を記録しておくと、追跡しやすい。

    4. ビルド環境は権限を絞り、記録を残す。権限を広げると、混入を許しうる。

頭の中で考える

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. 署名の検証が成功した部品でも、安全と言い切れない理由を、頭の中で説明してみよう。

    答えを開く

    署名は署名者と改ざんの有無を示すだけで、中身の安全や脆弱性の有無は示さない。間接的に使う部品の脆弱性も製品に影響する。署名の確認に加えて、SBOMを更新し、公表された脆弱性情報と照合する。

    思い浮かんだ要素にチェック

  2. SBOMだけでは脆弱性を防げない理由と、SBOMを活かす運用を説明してみよう。

    答えを開く

    SBOMは構成要素と依存関係（間接依存を含む）の一覧で、それだけでは脆弱性を防がない。公表された脆弱性情報と照合して初めて使える。SBOMを更新して継続的に照合すれば、見つかったときに影響する製品を速やかに特定できる。
