APIセキュリティ 守る場所は画面ではなくサーバ側

  1. APIは画面を介さず直接呼べるので、画面の制限は守りにならない。権限・入力・応答はサーバ側で守る。
  2. 認可は操作のたびに、オブジェクト単位・機能単位で確認する。認証済みでもすべてを許可しない。
  3. 回数制限は過剰な利用や負荷を抑えるが、認可の不備や必要以上の応答は防げない。

クイズ

  1. 動画で出た問題APIの保護の説明として、適切なものは？

    1. 画面の制限はAPIに及ばない

    2. 認証済みでも認可が要る

    3. 回数の制限で過剰な利用を抑える

    4. 検証はサーバ側で行う

  2. 一般会員のトークンで注文詳細のAPIを呼ぶと、注文番号を書き換えるだけで他の会員の注文が返ってくる（ダミー環境）。認証は正しく動いている。有効な対策はどれか。

    1. 期限を短くしても、有効なトークンの間は他人の注文を取得できる。問題は認可であって認証ではない。

    2. 回数制限は過剰な利用を抑えるが、認可の不備は防げない。1回の要求でも他人の注文が返る。

    3. 数字だけを受け付ける検証は入力の型を整えるだけ。他人の正しい注文番号なら、そのまま通る。

    4. 正解。操作のたびに、オブジェクト単位でサーバが権限を確認する。これがBOLAへの対策になる。

  3. 外部連携アプリに発行したトークンは、閲覧しか使わない用途なのに、書き込みや削除もできる範囲で、有効期限も長い。流出に備えた見直しとして最も適切なものはどれか。

    1. 正解。トークンは有効期限を短く、使える範囲を絞る。閲覧だけの用途なのに、書き込みや削除までできる範囲は広すぎる。

    2. 画面で隠してもAPIは直接呼べる。範囲はトークンとサーバ側で絞る必要がある。

    3. 回数を減らしても、書き込める権限そのものは残る。権限の範囲の問題を回数では解決できない。

    4. 応答の項目と、書き込みの権限は別の話。応答を絞っても、トークンの範囲は変わらない。

  4. 管理者用の機能のAPIを、一般の利用者のトークンで呼べることが判明した。回数制限はすでに十分に厳しく設定している。最も適切な対応はどれか。

    1. 制限しても認可の不備は防げない。1回でも呼べれば、管理機能が実行されてしまう。

    2. 正解。機能単位の判定を、サーバ側で行う。管理者用の機能を一般の利用者が呼べる不備への対策。

    3. 画面で隠しても、APIは直接呼べる。権限の確認はサーバ側で行う必要がある。

    4. 期限を短くしても、有効な間は呼べる。認証の強化は、機能ごとの認可の代わりにならない。

  5. 画面の入力欄は数量を1〜99に制限している。ところがAPIを直接呼ぶと、数量に -5 を指定したリクエストが受理され、在庫が増えてしまった（ダミー環境）。最も適切な対策はどれか。

    1. 正解。型・長さ・範囲をサーバ側で検証し、想定外の値は拒否する。画面の制限はAPIには及ばない。

    2. 画面を厳しくしても、APIを直接呼べば回避される。検証はサーバ側で行う。

    3. 回数を減らしても、1回で不正な値が受理されれば被害は出る。値の検証の代わりにならない。

    4. トークンの範囲は、どの操作を許すかの話。送られた値の妥当性は、入力検証で確認する。

  6. 認証・認可・入力検証は適切に実装済みで、応答も必要な項目に絞ってある。それでも1つのトークンから短時間に大量の要求が続き、API全体の負荷が高まっている。追加すべき対策として最も適切なものはどれか。

    1. 認可は権限の確認で、要求の量は変わらない。大量の要求そのものは認可の強化では抑えられない。

    2. 期限を短くしても、有効な間は大量に要求できる。要求数は抑えられない。

    3. 検証は値の妥当性の確認。正当な値による大量の要求は、検証を厳しくしても減らない。

    4. 正解。単位時間あたりの要求数を制限する回数制限は、過剰な利用や負荷の増大を抑える。

頭の中で考える

  1. 「画面でボタンを隠したので、権限のない操作はできない」という説明が成り立たない理由と、直し方を頭の中で説明してみよう。

    答えを開く

    APIは画面を介さず、プログラムから直接呼べるので、画面の制限はAPIに及ばない。権限・入力・応答はサーバ側で守る。具体的には、操作のたびにサーバがオブジェクト単位・機能単位で権限を確認する。

    思い浮かんだ要素にチェック

  2. APIの回数制限を入れても残るリスクを2つ挙げ、それぞれの対策を頭の中で説明してみよう。

    答えを開く

    回数制限は過剰な利用・総当たり・負荷を抑えるが、認可の不備と、必要以上の応答は防げない。認可の不備にはオブジェクト・機能ごとの権限確認、必要以上の応答にはサーバ側で必要な項目に絞る対策を重ねる。

会員検索APIの調査記録（ダミー）
店舗スタッフ用の、会員検索APIを調査した
画面の表示項目は、氏名と会員ランクのみ
応答のJSONには、この業務で使わない住所と電話番号も含む
認証とオブジェクト単位の認可は適切。通信もTLS保護済み
要件: 業務に不要な個人情報を、端末へ渡さない

適切な対策は、どれ？

答えを開く

サーバ側で、応答に含める項目を必要なものに絞る

よくある誤答

  • 画面側で、住所と電話番号を表示しない … 画面ではすでに非表示。応答には残る
  • トークンの有効期限を、さらに短くする … 応答に含まれる項目は変わらない
