#14 ・ 第2章 情報セキュリティにおける脅威

BOF攻撃の仕組み 戻りアドレスとsetuidの権限昇格

  1. BOFは、固定長バッファに長さを確認せず入力をコピーし、戻りアドレスまで上書きされることで起きる。
  2. setuidは所有者の権限で動く。所有者rootのsetuidにBOFがあり、入力を渡せると権限昇格になる。
  3. setuid rootだけでは成立せず、BOFでも得られるのは動いたプロセスの権限分。配置は環境で違う。

クイズ

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題setuid属性付きの実行ファイルを実行したとき、プロセスの実効ユーザーは？

    1. それは属性がない通常の場合

    2. 所有者がrootのときだけ

    3. ファイルの所有者

    4. 親プロセスは関係しない

  2. 関数内のローカル変数である固定長バッファへ、引数の文字列を長さの確認なしでコピーしている。x86系の典型的な配置で、バッファより長い入力が来たとき、起こりうることはどれか。

    1. 正解。書き込みは低位から高位へ進み、保存された値や戻りアドレスに届きうる。

    2. 書き込みはバッファより先（高位側）へ進むので、手前だけが書き換わるわけではない。

    3. 長さを確認していないので、切り捨てる処理は働かない。

    4. 書き換わるのはメモリ上の内容。ディスク上のファイルとは別の話。

  3. 所有者が一般ユーザー appuser で、setuid属性が付いたコマンドにBOFがあり、別の一般ユーザーに乗っ取られた。このとき動くコードの権限として最も適切なものはどれか。

    1. setuidはファイルの所有者の権限で動く。所有者がrootでなければrootにはならない。

    2. setuidが付いているので、実行者の権限のままではない。

    3. 親プロセスの所有者は関係しない。

    4. 正解。得られるのは、乗っ取られたプロセスが持っていた権限。ここでは所有者の権限。

  4. 所有者rootのsetuidコマンドが見つかった。脆弱性は確認されていない。評価として最も適切なものはどれか。

    1. setuid rootだけでは乗っ取れない。BOFなどの脆弱性が必要。

    2. 正解。脆弱性が無ければこの経路は成立しない。2つが重なると影響が大きくなる。

    3. 前提は、攻撃者がローカルでそのプログラムを実行でき、入力を与えられること。

    4. setgidは所有グループの権限で、rootグループとは限らない。「必ず」も言い過ぎ。

  5. BOFの解説図でスタックの配置を示すとき、説明として最も適切なものはどれか。

    1. 正解。配置はコンパイラ・アーキテクチャ・OSなどで異なる。図はx86系の例。

    2. バッファの直後とは限らない。間に保存された値などがあり、環境でも異なる。

    3. x86系の例では、戻りアドレスはバッファより高位にある。

    4. スタックは高位から低位へ伸びるが、書き込みは低位から高位へ進む。「必ず」も言い過ぎ。

  6. BOFの根本の原因として最も適切なものはどれか。

    1. setuidは被害を大きくする条件で、BOFの原因ではない。

    2. BOFは認証の突破ではなく、入力処理の不備で起きる。

    3. 戻りアドレスが書き換わる経路ではあるが、不備の原因は長さを確認しないコピー。

    4. 正解。長さを確認せずにコピーしているのが根本の原因。

頭の中で考える

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. 所有者rootのsetuidコマンドがあるだけでは、権限昇格は起きない。成立に必要な条件を、頭の中で説明してみよう。

    答えを開く

    そのプログラムに、入力の長さを確認しないなどのBOFの脆弱性があること、攻撃者がローカルでそのプログラムを実行して入力を渡せることが要る。2つが重なると、乗っ取られたコードがroot権限で動く。

    思い浮かんだ要素にチェック

  2. 長い入力が戻りアドレスに届く流れと、その結果を、頭の中で説明してみよう。

    答えを開く

    長さを確認せずにコピーするとバッファを超え、あふれた分が隣のメモリを上書きして戻りアドレスに届く。関数の終了時に書き換わった先へ移るので、脆弱なプロセスの権限で任意のコードが動く。

    思い浮かんだ要素にチェック

一般ユーザーが、非常に長い引数を渡して実行した
直前に当該コマンドが SIGSEGV で異常終了した記録あり
その直後、同じ端末のシェルが euid=0（実効UID=0）に
// 認証失敗の記録なし / ファイルのハッシュは配布時と一致

権限昇格が成立した原因として、適切なのは？

答えを開く

setuid rootのコマンドが入力長を確認せず、戻りアドレスを書き換えられた
