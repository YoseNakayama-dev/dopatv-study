#73 ・ 第6章 情報セキュリティ対策技術（2）アクセス制御と認証

主なID連携技術 認証と認可を分けて覚える

  1. SAMLは署名付きXMLで認証結果を伝え、OpenID ConnectはOAuth上に署名付きIDトークンで認証を加える。
  2. OAuth 2.0は認可の枠組みで、パスワードを渡さずトークンで権限を渡す。OAuth単体は本人確認の仕組みではない。
  3. 署名・宛先・期限を検証し、リダイレクトURIは事前登録と照合、state/nonceで対応づけ、スコープは最小に。

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題OpenID Connectの説明として、適切なのは？

    1. XMLで伝えるのはSAML

    2. OAuthを土台にしている

    3. OAuthの上に認証を加える

    4. 署名検証は省略しない

  2. アプリが、OAuth 2.0のアクセストークンを受け取れたことだけを根拠に、利用者のログインを成立させている。この設計の評価として最も適切なものはどれか。

    1. 署名付きのXMLで認証結果を伝えるのはSAMLである。OAuth単体は本人確認の仕組みではない。

    2. OAuthはパスワードを渡さずトークンで権限を渡す認可の枠組みで、OAuth単体は利用者の本人確認の仕組みではない。

    3. OAuth 2.0は認可の枠組みである。認証を加えたのはOpenID Connectである。

    4. 正解。OAuth単体は本人確認の仕組みではなく、認証を加えたのがOpenID Connectである。

  3. OAuth 2.0の認可の結果を返す側が、リダイレクトURIを検証せず、要求に付いたURIへそのまま結果を返している。対策として最も適切なものはどれか。

    1. 正解。リダイレクトURIは事前に登録したものと照合し、登録にないURLへは結果を返さない。

    2. 戻り先のURLを検証しないと、コードやトークンが攻撃者へ渡る。リダイレクトURIは事前登録したものと照合する。

    3. stateは要求と応答を結びつけるための対策で、リダイレクトURIの照合の代わりにはならない。

    4. トークンの期限を短くするのは漏えいの影響を小さくする対策で、リダイレクトURIの事前登録と照合は別に必要である。

  4. OAuth 2.0を使うアプリが、受け取った応答が自分の送った要求に対するものかを確かめたい。対策として最も適切なものはどれか。

    1. トークンの期限は短くする。要求と応答の対応づけには、stateやnonceを使う。

    2. 正解。stateやnonceで要求と応答を結びつける。

    3. 権限の範囲は最小限にする。広いほど漏えいの影響が大きい。

    4. リダイレクトURIは事前に登録したものと照合し、登録にないURLへは結果を返さない。要求と応答の対応づけはstateやnonceで行う。

  5. 外部アプリに、ストレージの広い範囲を操作できるスコープでアクセストークンを発行している。トークンが漏えいした場合に備える対策として最も適切なものはどれか。

    1. 権限の範囲が広いほど、漏えいの影響が大きい。

    2. 権限の範囲は最小限、トークンの期限は短くする。広く長くすると漏えいの影響が大きくなる。

    3. トークンは持っているだけで使えてしまう。権限の範囲は最小限にする。

    4. 正解。スコープを最小限にし、トークンの期限を短くして、漏えいの影響を小さくする。

  6. サービス側が、SAMLのアサーションの署名を検証せず、中のメールアドレスだけで利用者を特定してログインさせている。評価と対応として最も適切なものはどれか。

    1. 正解。署名を検証しないと偽の認証結果を受け入れる。署名・宛先・有効期限を検証する。

    2. SAMLは署名付きのXMLで認証結果を伝えるもので、署名を検証しないと偽の認証結果を受け入れる。

    3. 署名の未検証で偽の認証結果を受け入れる。署名、宛先、有効期限のすべてを検証する。

    4. 署名を付けるのはIdPだが、その署名が正しいかを確かめるのは受け取る側である。受け取る側が検証しないと、偽の認証結果を受け入れる。

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. OAuth 2.0とOpenID Connectの違いを、認証と認可の言葉で、頭の中で説明してみよう。

    答えを開く

    OAuth 2.0は認可の枠組みで、パスワードを渡さずアクセストークンで権限を渡す。OAuth単体は本人確認の仕組みではない。OpenID ConnectはOAuthの上に認証を加え、署名付きのIDトークンで認証結果を伝える。

  2. リダイレクトURIを検証しないとなぜ危ないか、またどう防ぐかを、頭の中で説明してみよう。

    答えを開く

    戻り先のURLを検証しないと、コードやトークンが攻撃者へ渡る。リダイレクトURIを事前に登録して照合し、登録にないURLへは結果を返さない。

写真閲覧アプリの連携に関する調査記録（ダミー）
現状: 外部の写真閲覧アプリが、利用者のクラウド上の写真を表示する
外部アプリに、利用者のパスワードは渡したくない
外部アプリに、写真の閲覧以外の操作はさせたくない
クラウド側は、利用者の同意に基づく権限付与に対応している
要件: 権限は利用者が把握できる範囲に限り、有効期間に上限を設ける

要件を満たす方法として、適切なのは？

答えを開く

利用者の同意のもと、閲覧に限り期限をつけた許可証を外部アプリに発行する

よくある誤答

  • 利用者のパスワードを外部アプリに登録し、代わりにログインさせる … パスワードを渡さない要件に反する
  • ストレージ全体の管理者アカウントを外部アプリと共有する … パスワードも渡すことになり、範囲も期限も絞れない
