#120 ・ 第8章 システム開発におけるセキュリティ対策

ECMAScript関連技術 オリジン・CORS・JSON・DOMの扱い

  1. オリジンはスキーム・ホスト名・ポートの組。別オリジンの応答は原則読めないが、送信は止まらない。
  2. CORSは許可したオリジンにだけ読取りを許す。Cookie付きは特定のオリジンを指定し、認可の代わりにならない。
  3. JSONはJSON.parseで解析し、DOMへはtextContentで出す。JSONPは提供元のコードを実行する古い方式。

用語カード

クイズ

  1. 動画で出た問題ECMAScript関連の説明として、適切なものは？

    1. スキームとポートも含む

    2. CORSは認可の代わりではない

    3. JSONPは提供元のコードを実行

    4. JSON.parseで解析する

  2. 社員向けポータルのAPIは、Cookieで認証し、更新の要求を受け付ける。設計レビューで「同一オリジンポリシーがあるので、他サイトからの要求は問題にならない」と説明された。この説明への指摘として適切なものはどれか。

    1. 同一オリジンポリシーが制限するのは読み取りで、リクエストの送信自体は止めない。

    2. 正解。送信は届いてしまうので、その被害にはCSRF対策など別の備えが要る。

    3. 事前確認（プリフライト）が行われるのは、ヘッダ付きの要求やPUT・DELETEなど一部の要求。単純なGETでは行われない。拒否される保証にもならない。

    4. CORSは読み取りを許可する仕組みで、ブラウザの制限の緩和にあたる。送信による被害を防ぐものではない。

  3. http://shop.example.test のページから、https://shop.example.test のAPIを呼ぶと、CORSの設定が無いためブラウザが応答の読み取りを拒否した。原因の説明として適切なものはどれか。

    1. 正解。オリジンはスキーム・ホスト名・ポート番号の組。httpとhttpsでスキームが違えば、別のオリジンになる。

    2. オリジンはホスト名だけでは決まらない。スキームが違えば、ホスト名が同じでも別のオリジンになる。

    3. Cookie付きの要求でも、サーバが特定のオリジンを指定して許可すれば読み取れる。オリジンを問わず禁止されるわけではない。

    4. 読み取りの制限はブラウザの仕組みで、サーバ側の認可の有無とは別のもの。

  4. 検索ページのJavaScriptが、URLの一部を取り出し、innerHTMLで結果欄に表示している。サーバ側のコードには、その値を出力する箇所がない。判断として適切なものはどれか。

    1. innerHTMLに入力を渡すと、ブラウザ上のJavaScriptだけでもDOM Based XSSの原因になる。サーバ側に出力箇所がなくても起こりうる。

    2. 原因はブラウザ上でinnerHTMLに入力を渡す書き込み側にある。サーバ側の処理を強化しても、この箇所は直らない。

    3. 正解。入力値はtextContentで出す。innerHTMLやdocument.writeに入力を渡さない。

    4. JSON.parseはJSON文字列の解析に使うもの。その結果をinnerHTMLに渡せば、HTMLとして解釈される点は変わらない。

  5. APIは、Access-Control-Allow-Originを自社ポータルのオリジンだけに限定している。ところがログには、ブラウザではないクライアントが、認可の確認なしにAPI応答を取得した記録がある。この現象の説明として適切なものはどれか。

    1. プリフライトは、ブラウザが一部の要求の前に行う事前確認。ブラウザ以外のクライアントによる取得とは関係しない。

    2. 同一オリジンポリシーもブラウザの制限。ブラウザを更新しても、ブラウザ以外からの呼び出しには効かない。

    3. 自社のみの許可は設計意図どおり。それはブラウザが読み取れる範囲の話で、ブラウザ以外のクライアントには効かない。

    4. 正解。CORSはブラウザの制限の緩和で、サーバ側の認可の代わりにならない。ブラウザ以外のクライアントは制限されない。

  6. 旧機能が、取引先の外部サイトのデータを、script要素を使うJSONPで取得している。提供元のサーバが改ざんされた場合に、考えられることはどれか。

    1. 正解。JSONPは提供元のコードをそのまま実行する方式。信頼できない提供元には使えず、CORSなどに置き換える。

    2. JSONPはscript要素で読み込むため、応答はデータではなくコードとして実行される。データの改ざんだけでは済まない。

    3. script要素による読み込みは、別オリジンの応答を読み取る方式として使われてきた。そのため、読み取れずに破棄されるわけではない。

    4. JSONPはCORSを使う方式ではない。CORSの許可リストの設定は、この読み込みを止めない。

頭の中で考える

  1. 同一オリジンポリシーが防ぐものと、防がないものを、頭の中で説明してみよう。

    答えを開く

    防ぐのは、別オリジンの応答をスクリプトから読むこと。リクエストの送信自体は止めないので、他サイトから送られた要求は届く。その被害にはCSRF対策など別の備えが要る。

    思い浮かんだ要素にチェック

  2. Cookie付きでAPIを呼ばせる場合に、CORSをどう設定すべきか、その理由とともに頭の中で説明してみよう。

    答えを開く

    許可リストと照合した特定のオリジンだけを指定する。Cookie付きでは*は使えず、要求のOriginをそのまま返すと任意のオリジンに許可を与える。CORSは認可の代わりにならないので、サーバ側の認可も別に行う。

    思い浮かんだ要素にチェック

午後問題にチャレンジ

社内ポータルの通信記録（ダミー）
ポータルは、Cookie付きでAPIを呼び出して表示する
APIは、Originの値をそのまま許可し、Cookieも許可
外部サイトのスクリプトが、社員のAPI応答を読んだ
その要求はGETで、事前確認（プリフライト）はなし
要件: Cookie付きのまま、自社ポータルだけに読ませる

適切な対策は、どれ？

答えを開く

許可リストと照合して、自社ポータルのオリジンだけを許可する

よくある誤答

  • 許可を*にする … Cookie付きでは使えず、使えても全オリジンに読ませてしまう
  • 事前確認への応答を拒否する … 読まれたGETでは事前確認は行われない
