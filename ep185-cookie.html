#85 ・ 第8章 システム開発におけるセキュリティ対策

Cookieの扱い 属性で守る範囲が違う

  1. Cookieはサーバが渡し、ブラウザが保存して自動で送り返す。値は書き換えられるので権限や個人情報は入れない。
  2. Secureは送信をHTTPSに限り、HttpOnlyはスクリプトから読めなくし、SameSiteは他サイトからの送信を制限する。
  3. どの属性も補助。HttpOnlyでもXSSは残り、SameSiteにはトークンの確認も併用し、サーバ側の期限は長くしない。
用語 8クイズ 6考える 2午後本

用語カード

クイズ

  1. 動画で出た問題SameSite属性の説明として、適切なのは？

    1. 他サイトからの送信を制限する

    2. それはSecure属性

    3. それはHttpOnly属性

    4. 期間を指定するのは有効期限

  2. ログイン後のセッションIDを入れたCookieに、HttpOnly だけを付けている。サイトはHTTPSで配信しているが、利用者が暗号化されないHTTPで接続する場合がある。評価として適切なのはどれか。

    1. HttpOnlyはスクリプトから読めなくする属性で、送る通信の種類は制限しない。送信をHTTPSに限るのはSecure。

    2. SameSiteは他サイトからのリクエストでの送信を制限する属性。HTTPかHTTPSかを制限するのはSecure。

    3. 正解。Secureを付けないと、暗号化されない通信でもCookieが送られる。HTTPで接続されるとIDが送られてしまう。

    4. HttpOnlyは送る通信を制限しない。HttpOnlyの有無でHTTPSだけに送られるようにはならない。

  3. XSSの脆弱性が残るページで、セッションIDのCookieに HttpOnly を付けた。報告書には「これでXSS対策は完了」とある。評価として適切なのはどれか。

    1. HttpOnlyはスクリプトからCookieを読めなくする属性で、XSSそのものは防げない。

    2. 正解。HttpOnlyがあってもXSSの脆弱性は残る。スクリプトによる画面の改ざんなどは防げない。

    3. SameSiteは他サイトからの送信を制限する属性で、XSSの脆弱性は直らない。

    4. Secureは送信をHTTPSの通信に限る属性で、スクリプトによる画面の改ざんは防げない。

  4. ログイン済みのサイトで、CSRF対策としてセッションIDのCookieにSameSite属性を付けた。トークンの確認は実装していない。評価として適切なのはどれか。

    1. SameSiteはCSRF対策の補助。トークンの確認も併用する。

    2. 盗聴対策はSecure。SameSiteは他サイトからのリクエストでの送信を制限し、CSRF対策の補助になる。

    3. スクリプトから読めなくするのはHttpOnly。SameSiteは他サイトからの送信を制限する。

    4. 正解。SameSiteはCSRF対策の補助で、トークンの確認も併用する。

  5. あるサイトはCookieに role=admin と会員の氏名を保存し、サーバはその値を信用して権限を判定している。この設計への評価として適切なのはどれか。

    1. 正解。Cookieの中身は利用者が書き換えられるので、権限や個人情報は直接入れない。セッションIDは推測されにくい値にする。

    2. HttpOnlyはスクリプトからの読み取りを禁じ、Secureは送信をHTTPSに限る属性。利用者が値を書き換える問題は別。

    3. 期限の長短は中身の問題と別。権限や個人情報を直接入れること自体が、改ざんされる原因になる。

    4. SameSiteは他サイトからのリクエストでの送信を制限する属性で、利用者が値を書き換える問題は別。

  6. 盗まれたセッションIDが長く使われる被害を抑えたい。現在、サーバ側のセッション有効期限が長く設定されている。対応として適切なのはどれか。

    1. HttpOnlyはスクリプトからの読み取りを禁じる属性で、盗まれないことの保証ではない。XSSそのものも防げない。

    2. 正解。サーバ側の有効期限が長いと、盗まれたIDが長く使われる。必要以上に長くしない。

    3. サーバ側の有効期限が長いままだと、盗まれたIDは長く使われる。サーバ側を見直す必要がある。

    4. 推測されにくい値にするのはIDを当てられにくくする対策。盗まれたIDが長く使われる問題は、サーバ側の期限に関わる。

頭の中で考える

  1. 「HttpOnlyを付けたからXSS対策は済み」と言えない理由と、Secure・HttpOnly・SameSiteの守る範囲の違いを、頭の中で説明してみよう。

    答えを開く

    HttpOnlyはスクリプトからCookieを読めなくするだけで、XSSの脆弱性は残り、スクリプトによる画面の改ざんなどは防げない。Secureは送信をHTTPSに限り、SameSiteは他サイトからの送信を制限する。三つは守る範囲が違うので使い分ける。

    思い浮かんだ要素にチェック

  2. セッションIDをCookieで扱う設計で、値・属性・期限について何をすべきか、頭の中で説明してみよう。

    答えを開く

    値は推測されにくいIDだけにして、権限や個人情報は入れない。属性はSecureとHttpOnlyを付け、SameSiteで他サイトからの送信を制限し、CSRFにはトークンの確認も併用する。サーバ側の有効期限は必要以上に長くしない。

よくある誤答

  • CookieにSecure属性だけを付ける … Secureは送信をHTTPSに限る設定で、スクリプトの読み取りは防げない
  • CookieにSameSite属性を付ける … 他サイトからの送信を制限する設定で、スクリプトの読み取りは防げない

本で読む

  • 8.4.4 Cookieの扱い

Secure・HttpOnly・SameSiteそれぞれが何を守り、何を守らないかを対応づけて読む。中身と期限の注意点も確かめる。
