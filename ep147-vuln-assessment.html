脆弱性診断の概要と実施 範囲と時点が肝

  1. 脆弱性診断は、攻撃される前に脆弱性を見つけて対処する。ネットワーク診断とWebアプリ診断がある。
  2. 計画で範囲を合意し、自動と手動を組み合わせて実施。報告の深刻度に資産の重要度と公開を加味する。
  3. 結果は診断した範囲と時点のもの。許可と本番への配慮が要り、変更のたびに再診断する。

クイズ

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題脆弱性診断の実施として、適切なのは？

    1. 変更のたびに再診断が必要

    2. 本番の停止や、問題の原因に

    3. 実施前に、範囲などを合意

    4. ロジックの不備は見落としやすい

  2. 公開中のサーバ群について、OSやミドルウェアの状態と、開いている通信の状態を調べたい。診断の種類として最も適切なものはどれか。

    1. Webアプリ診断の対象は画面・入力の処理・認証とセッションの扱い。サーバの状態を調べるのはネットワーク診断。

    2. 正解。サーバや機器のOS・ミドルウェア・通信の状態を調べるのはネットワーク診断。

    3. ホワイトボックスは調べ方（方式）の区分で、診断の種類ではない。

    4. ブラックボックスも方式の区分。種類（ネットワーク・Webアプリ）とは別の軸。

  3. 診断報告書に、深刻度が高い脆弱性が非公開の検証機に、深刻度が中の脆弱性がインターネット公開中の基幹サーバにあった。優先順位の付け方として最も適切なものはどれか。

    1. 深刻度だけで決めない。資産の重要度や公開の有無も加味する。

    2. 公開の有無は考慮するが、深刻度を無視してはいけない。両方を見る。

    3. 件数で決める根拠はない。深刻度と、資産の重要度や公開の有無で決める。

    4. 正解。報告の深刻度に、資産の重要度や公開の有無も加味して優先順位を付ける。

  4. 自社システムの一部はクラウド上にあり、一部は委託先が運用している。診断事業者に診断を依頼する前に確認すべきこととして最も適切なものはどれか。

    1. 正解。許可のない診断は問題になる。委託先やクラウドの規約・同意も確認する。

    2. 委託先やクラウドの規約もあり、許可なく診断してよいとは言えない。

    3. 事業者の経験は許可の代わりにならない。範囲は発注側と事業者の合意と、規約・同意で決まる。

    4. 確認は診断の前に行う。実施後に確認するのでは、問題になりうる診断をすでに行っている。

  5. 診断で指摘された脆弱性を修正した。その後の対応として最も適切なものはどれか。

    1. 結果は診断した範囲と時点のもの。変更のたびに再診断が必要になる。

    2. 正解。修正したあとは再診断で解消を確認する。変更のたびにも再診断が必要。

    3. 解消の確認は再診断で行う。自己申告では確認にならない。

    4. ツールには誤検知や検出漏れがあり、業務ロジックの不備は見つけにくい。

  6. 自動診断ツールの結果が「指摘なし」だった。結果の受け止め方として最も適切なものはどれか。

    1. 自動診断は網羅的で短時間だが、誤検知や検出漏れがある。

    2. 自動診断は網羅的で短時間という長所がある。使わないのではなく、手動診断で補う。

    3. ツールは業務ロジックの不備を見つけにくい。指摘なしでは確認できていない。

    4. 正解。自動診断は誤検知・検出漏れがあり、業務ロジックの不備は見つけにくい。専門家の手動診断で補う。

頭の中で考える

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. 診断の指摘をすべて直したのに、公開後に別の不備が見つかることがある。その理由を、診断の範囲と時点の観点で、頭の中で説明してみよう。

    答えを開く

    診断結果は診断した範囲と時点のものだけ。診断計画に載っていない画面などは診断されない。システムを変更したら、再診断が必要になる。

    思い浮かんだ要素にチェック

  2. 自動診断だけに頼ってはいけない理由と、本番環境で診断するときの配慮を、頭の中で説明してみよう。

    答えを開く

    自動診断は網羅的で短時間だが、誤検知や検出漏れがあり、業務ロジックの不備は見つけにくいので、専門家の手動診断で補う。本番では負荷やデータの変更に配慮し、検証環境や影響の少ない時間帯を選ぶ。

診断計画の対象画面: トップ、ログイン、検索

診断で見つからなかった原因として、適切なのは？
