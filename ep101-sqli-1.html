#1 ・ 第2章 情報セキュリティにおける脅威

SQLインジェクション① 攻撃が成立する仕組み

  1. 入力を文字列連結でSQL文に組み込むと、入力が値ではなく構文として解釈されうる。
  2. UNIONで別表を読むには列数と型の互換が要る。数値の入力はクォートが無くても成立する。
  3. 影響（漏えい・改ざん・認証回避など）の大きさは、実装とDBアカウントの権限しだい。
用語カード 8クイズ 6考える 2午後問題本で読む

用語カード

用語を見て意味を言えるか試し、タップで裏返します。「覚えた」を続けるほど定着度が上がり、「まだ」で最初に戻ります。

クイズ

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題SQLインジェクションが成立する直接の原因は？

    1. 入力が構文として解釈される実装が原因

    2. パスワード強度は別の問題

    3. WAFは補助的な対策

    4. HTTPSは通信路の保護

  2. ログイン処理は SELECT * FROM users WHERE id='（入力ID）' AND pw_hash='（入力パスワードのハッシュ値）' を文字列連結で組み立て、行が返れば成功とする。パスワード条件を無効化する入力を送り込める欄はどれか。

    1. パスワードはハッシュ値に変換されてから連結されるので、入力したクォートなどはSQLに届かない。

    2. パスワード欄の入力はハッシュ値に変わるため、構文を書き換えられない。

    3. ID欄は入力がそのまま連結されるので、無害化されていない。

    4. 正解。ID欄の入力はそのまま連結されるので、クォートで閉じて後ろの条件をコメントで無効化できる。

  3. 商品検索のSQLは3列を返す。攻撃者が UNION SELECT で users 表の name と pass の2列を一覧に出したい。成立について最も適切なものはどれか。

    1. 2列のままでは失敗するが、列数をそろえる工夫ができれば成立しうるので「成立しない」は言い過ぎ。

    2. UNIONは別の表のSELECTを後ろに足せる。

    3. 正解。UNIONの成立には列数の一致と型の互換が必要。条件を満たせば別の表を読める。

    4. 列数が一致しないとエラーになる。自動では補われない。

  4. 画面には検索結果もエラーも出ない作り。ある入力を送ったときだけ、応答が数秒遅れることが繰り返し確認された。最も疑うべきものはどれか。

    1. 特定の入力でだけ繰り返し遅れるなら、入力でDBの処理が変わっている疑いがある。

    2. 正解。結果が見えなくても、応答の違いや待ち時間の差から情報を推測する手法がある。

    3. 特定の入力で遅れる現象で、量で止める攻撃とは手がかりが違う。

    4. WAFの挙動と決めつける根拠はない。入力で処理が変わる点を疑う。

  5. 検索機能にSQLインジェクションがある。アプリが使うDBアカウントには、商品表と会員表の SELECT 権限だけが付いており、ほかの実行権限や拡張機能は無効。想定すべき被害として最も適切なものはどれか。

    1. 正解。影響の大きさはクエリの用途とDBアカウントの権限しだい。読める範囲の情報が漏れうる。

    2. 改ざんや消去には更新や削除の権限が要る。

    3. OSコマンド実行はDBMSや付与された権限しだいで起こりうる被害で、この前提では条件を満たさない。

    4. 会員表を読めるなら漏えいが起きる。被害が無いとは言えない。

  6. アクセスログに、検索語へシングルクォートを1文字だけ入れたリクエストと、その直後のSQL構文エラーらしき応答が並んでいた。攻撃者の狙いとして最も適切なものはどれか。

    1. クォート1文字では表示崩しの狙いと結びつかない。

    2. 1件のリクエストで、量で止める狙いとは考えにくい。

    3. 正解。クォートが文字列の終わりと読まれて文法が壊れれば、連結されている手がかりになる。詳細なエラーは組み立て方のヒントにもなる。

    4. スクリプトを埋め込むならタグなどが必要。クォート1文字は文法を壊して試す動き。

頭の中で考える

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. SQLインジェクションが成立する条件を、2点に分けて頭の中で説明してみよう。

    答えを開く

    入力値を文字列連結などでSQL文に組み込み、リテラルの処理（エスケープや数値の確定）が不十分なこと。その結果、入力が値としてではなく、SQLの構文として解釈されること。

    思い浮かんだ要素にチェック

  2. 「エラーメッセージを画面に出さない」がSQLインジェクションの根本対策にならない理由を頭の中で説明してみよう。

    答えを開く

    エラーを隠しても、入力が構文として解釈される原因は残る。応答の違いや待ち時間から推測するブラインドSQLインジェクションも成立しうるため、ヒントを減らす保険的な対策にとどまる。
