#9 ・ 第7章 情報セキュリティ対策技術（3）暗号

TLS 1.3 通信を守る仕組みの何が変わった？

  1. TLS 1.3は静的RSA・静的DHや圧縮を廃止し、残る対称暗号をAEADにそろえた。
  2. 公開鍵ベースの鍵交換はすべて前方秘匿性を持ち、長期鍵が漏れても過去の通信の鍵は復元されない。
  3. 0-RTTは往復を省くが前方秘匿でなく再送対策も弱い。TLSだけでアプリの脆弱性は消えない。

クイズ

選ぶと、すべての選択肢について「なぜ正しいか・なぜ違うか」が出ます。間違えた問題は復習に入ります。

  1. 動画で出た問題前方秘匿性を持つ鍵交換として適切なのは？

    1. 静的な方式なら、長期鍵の漏えいで過去も危険

    2. 使い捨てのDH鍵ペアで共有し、破棄する

    3. 圧縮は廃止。前方秘匿性とは別

    4. 0-RTTは前方秘匿ではなく、再送の恐れもある

  2. 「サーバの長期秘密鍵が漏れても、過去の通信を守る」という要件がある。TLS 1.3 の構成の評価として最も適切なものはどれか。

    1. 誤り。0-RTT で送るデータは前方秘匿ではない。有効にしても、全通信が前方秘匿にはならない。

    2. 誤り。署名は相手の確認の話で、鍵交換の前方秘匿性とは別。

    3. 正解。公開鍵ベースの鍵交換は前方秘匿性を持つが、0-RTT で送るデータは対象外で、再送対策も弱い。

    4. 誤り。ServerHello 以降の暗号化は前方秘匿性の理由ではない。理由は使い捨ての鍵共有にある。

  3. TLS 1.3 のサーバで 0-RTT を許可しており、決済確定の POST を early data のまま処理している。評価として最も適切なものはどれか。

    1. 正解。0-RTT のデータは再送対策が通常のデータより弱い。状態を変える処理は避け、使うなら冪等な処理に限る。

    2. 誤り。暗号化されていても、攻撃者による再送は起こりうる。

    3. 誤り。再開の接続が前提だが、early data の再送対策は通常のデータより弱い。

    4. 誤り。early data は前方秘匿ではない。冪等でない処理は、再送の影響をそのまま受ける。

  4. 中間のネットワーク機器が、TLS 1.2 では平文だった ServerHello 以降のハンドシェイクのメッセージを見て、通信を分類していた。TLS 1.3 に移行した場合の説明として最も適切なものはどれか。

    1. 誤り。暗号化されるのは ServerHello 以降。ServerHello までは平文なので、開始の観測はできる。

    2. 誤り。ServerHello 以降は暗号化されるので、平文を前提にした分類は使えなくなる。

    3. 誤り。暗号化は一部のメッセージだけでなく、ServerHello 以降のハンドシェイクメッセージに及ぶ。

    4. 正解。ServerHello までは平文だが、以降は暗号化される。平文を前提にした分類は使えなくなる。

  5. 帯域の節約のため、TLS 1.3 の通信で TLS の圧縮機能を有効にするよう求められた。対応として最も適切なものはどれか。

    1. 誤り。TLS 1.3 では圧縮が廃止されており、標準機能として利用できない。

    2. 正解。TLS 1.3 は圧縮を廃止している。TLS の設定としては有効にできない。

    3. 誤り。AEAD は暗号化と改ざん検出の方式で、圧縮の代わりにはならない。

    4. 誤り。静的RSAも圧縮も TLS 1.3 では廃止されており、組み合わせて有効にはできない。

  6. TLS 1.3 のみを許可した Web サイトで、利用者の入力をエスケープせずに出力するページがあり、XSS が確認された。評価として最も適切なものはどれか。

    1. 正解。TLS は通信路の保護で、入力をエスケープせず出力するアプリの脆弱性は TLS では消えない。

    2. 誤り。暗号化は通信路の盗み見への対策で、入力値のスクリプトは無効化されない。

    3. 誤り。AEAD は通信中の改ざんを検出するもので、サーバが出力する内容の安全性は保証しない。

    4. 誤り。前方秘匿性は過去の通信の鍵の話で、スクリプトの実行とは関係しない。

頭の中で考える

書かなくて大丈夫です。答えを頭の中で組み立ててから開き、要素がそろっていたか確かめます。

  1. TLS 1.3 でも 0-RTT を有効にする前に確かめておくべきことを、頭の中で説明してみよう。

    答えを開く

    0-RTT の early data は前方秘匿ではなく、攻撃者に再送されうるうえ、再送対策も通常のデータより弱い。状態を変える処理は避け、使うなら冪等な処理に限る。用途を絞って考える。

    思い浮かんだ要素にチェック

  2. 「TLS 1.3 にすればアプリは安全」と言えない理由を、頭の中で説明してみよう。

    答えを開く

    TLS は通信路の保護で、盗み見・改ざん・なりすましへの対策にあたる。アプリケーション自体の脆弱性は、TLS を使っても消えない。古い方式や弱い暗号を無効にし、前方秘匿性を持つ設定を選ぶことと、アプリの脆弱性対策は別に必要。

    思い浮かんだ要素にチェック

長期鍵の漏えい後に、過去の通信が解読できた設計上の理由は？

答えを開く

長期の秘密鍵から、通信鍵を復元できる鍵交換だった

よくある誤答

  • サーバ証明書の署名が弱かった … 署名は相手の確認の話。鍵交換とは別
  • 暗号文を保存されたこと自体 … 保存だけでは解読できない。鍵の復元が原因
